# Uncle Bob tools in the Rust MVP workflow

**Checked:** 2026-11-19. This report uses the requested first-party repositories and their current default-branch documentation. No tools were installed or run.

## Decision

Keep the product and its normal unit and integration tests in Rust. Three requested tools have documented Rust support: **Mutator** for source mutation, **Crapper** for complexity/coverage metrics, and **Dryer** for duplicate-code candidates. Mutator requires Crapper beside it. **SCRAP** is specifically a Speclj/Clojure spec analyzer; it cannot analyze Rust tests. The two acceptance systems are extensible, but neither supplies a ready Rust fixture/runtime: APS leaves the project-specific acceptance generator and runtime to the project, while AgNesse needs a Rust process that speaks Slim. They are separate systems and do not share a built-in adapter.

That distinction matters to the literal “use all these tools” requirement. A small Speclj wrapper suite can exercise a Rust CLI smoke path and be analyzed by SCRAP, but SCRAP’s result then describes the Clojure wrapper specs, not the Rust test suite. If all named tools must be invoked, use that narrow harness and keep it clearly scoped. Avoid adding unrelated Clojure code solely to claim Rust coverage.

## Dependencies and hand-offs

- **Rust baseline:** cargo fmt --check, cargo clippy --all-targets -- -D warnings, and cargo test remain the project’s regular feedback loop.
- **Mutator → Crapper:** Mutator’s README explicitly requires the Crapper checkout beside Mutator. Crapper supplies namespace/function names and coverage data; Mutator writes mutation snapshots under .metrics/mutate/. These Python tools are scripts around Cargo, not Cargo plugins.
- **Crapper/Mutator → UML Viewer:** the viewer consumes CRAP/coverage and mutation snapshots and joins by namespace/function. It is a consumer of those files, not a dependency for generating them. Dryer is independent and its duplicate-candidate report is not shown by the viewer. [Mutator snapshot format](https://github.com/unclebob/mutator/blob/main/README.md#snapshot), [viewer overlay](https://github.com/unclebob/uml-viewer/blob/master/README.md#language-graphs).
- **APS → Rust runner:** the parser and optional Gherkin IR DRY checker can be used as supplied; generator, runtime, handlers, and adapter are the Rust project’s responsibility. The adapter should execute the same generated test entrypoints against each mutated IR value.
- **AgNesse → Rust fixture process:** the Java host launches a custom Slim server through COMMAND_PATTERN; this is a separate integration from APS. The guide’s Python example establishes the process/protocol seam, not ready-made Rust support.
- **SCRAP → Speclj only:** the Clojure CLI dependency is only justified if a separate Speclj wrapper suite is deliberately retained. SCRAP does not sit in the Rust test pipeline.

## Minimal practical workflow

1. Keep product behavior and ordinary tests Rust-native. Run formatting, Clippy, and cargo test in regular verification.
2. For edited Rust modules, run **./crapper path** and review high-risk functions; choose a coverage backend explicitly, since the default may install cargo-llvm-cov. Run **./mutator path** on a narrow scope first, then widen only if the run time is acceptable. Review **./dryer --changed** candidates manually.
3. Use APS Gherkin for a small set of observable acceptance behaviors after the selected audio path and user controls are known. Implement its Rust generator/runtime/step handlers and a runner adapter that invokes Cargo. Run Gherkin data mutation as a separate, deliberate test-quality pass; it complements source mutation.
4. Use AgNesse only for interactive/device acceptance pages if they provide value. The minimal Rust integration is a small Slim process launched by AgNesse’s COMMAND_PATTERN; it must implement the documented Slim wire behavior and call the product. Do not expect APS features to run in AgNesse automatically.
5. To satisfy the literal all-tools requirement, keep a very small Speclj contract wrapper that launches a no-hardware Rust CLI smoke path and run **clj -M:scrap spec**. Treat SCRAP’s output as feedback on that wrapper only. If the team is not willing to maintain Clojure specs, record SCRAP as not applicable to this Rust project rather than treating Rust tests as analyzed.
6. Add UML Viewer only if visual exploration of Crapper/Mutator snapshots and architecture is actually useful.

The minimum all-tools setup therefore carries Rust/Cargo, Python 3.11+, and (if all tools are invoked) Babashka or Go, Java 21, and Clojure CLI. That stack is materially larger than a Rust-only loop; the explicit tool requirement should be considered a project constraint, not evidence that every tool analyzes Rust directly.

## Maturity and pinning

The repositories document runnable commands and test suites, but their GitHub Releases endpoints were empty when checked on 2026-11-19. Mutator, Crapper, and Dryer declare package version 0.1.0; their manifests require Python 3.11+. APS includes Babashka and Go tests; AgNesse documents Gradle unit/acceptance/build tasks. This is evidence of active, tested source trees, not a stability guarantee. Pin the exact tool commits in project setup and expect their CLI, mutation rules, and snapshot formats to evolve.
