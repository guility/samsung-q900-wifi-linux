# Linux audio graph for synchronized dual output

Research date: 2026-11-19  
Issue: [Choose the Linux audio graph for synchronized dual output](https://github.com/guility/samsung-q900-wifi-linux/issues/4)

## Decision

Use PipeWire's `libpipewire-module-combine-stream` in `sink` mode to expose one virtual output with the local sink and the connected Q900T sink as its members. Enable `combine.latency-compensate`, then make that virtual sink the WirePlumber default. This gives ordinary PipeWire streams and PulseAudio-compatible clients handled by `pipewire-pulse` one system playback route; PipeWire creates a playback stream for each matched physical sink. The module's documented purpose is to create a virtual sink that forwards audio to other sinks, and it supports matching those sinks by properties. [PipeWire Combine Stream docs](https://pipewire.pages.freedesktop.org/pipewire/page_module_combine_stream.html), [WirePlumber linking policy](https://pipewire.pages.freedesktop.org/wireplumber/policies/linking.html), [PipeWire Pulse modules](https://pipewire.pages.freedesktop.org/pipewire/page_pulse_modules.html)

This is graph routing, not an application audio loop. PipeWire owns the PCM paths and format/channel conversion, while WirePlumber owns endpoint linking, default selection, and ordinary reconnect behavior; the Rust program need not capture and rewrite every application's samples. WirePlumber links new playback streams to the configured default sink unless the stream has a specific target. [WirePlumber linking policy](https://pipewire.pages.freedesktop.org/wireplumber/policies/linking.html)

## Capture and routing choices

| Option | What it covers | Delay control | Use |
| --- | --- | --- | --- |
| Combined virtual sink | Streams routed to that default sink, including normal desktop audio and Pulse-compatible apps | Automatic compensation based on the target streams' reported delays | Recommended starting graph |
| Sink-monitor loopback | The post-mix audio sent to one selected sink | One `target.delay.sec` per loopback | Useful for mirroring one sink or for explicit per-output calibration |
| Selected-stream capture | One chosen application/stream | Application-specific stream configuration | Only when the product needs per-app behavior |
| Monitor every physical sink | Audio on multiple device monitors | Requires a monitor/aggregation policy and duplicate-path handling | Use only if apps must bypass the default virtual sink |

A combined sink is system-wide for applications that use the normal PipeWire routing path and follow the default sink. Applications that explicitly select a physical sink, or bypass PipeWire, are outside that route; those need a routing rule or a monitor path of their own. WirePlumber's `target.object` property can select either a device node or another stream node. Sink monitor ports expose audio being sent to a sink, and a capture stream can request the sink monitor with `stream.capture.sink=true`. [WirePlumber linking policy](https://pipewire.pages.freedesktop.org/wireplumber/policies/linking.html), [PipeWire loopback docs](https://pipewire.pages.freedesktop.org/pipewire/page_module_loopback.html), [PipeWire monitor-port settings](https://pipewire.pages.freedesktop.org/wireplumber/daemon/configuration/settings.html)

PipeWire's stable Combine Stream documentation describes `sink`, `source`, `capture`, and `playback` modes. The current development documentation and source also contain a `monitor` mode that aggregates sink monitor ports, but that mode is absent from the stable docs page; check the installed PipeWire version before depending on it. Even with such an aggregator, explicitly routed streams and duplicate paths need deliberate handling. [Stable Combine Stream docs](https://pipewire.pages.freedesktop.org/pipewire/page_module_combine_stream.html), [development Combine Stream docs](https://docs.pipewire.org/devel/page_module_combine_stream.html)

## Synchronization and calibration

With `combine.latency-compensate=true`, PipeWire inserts delay buffers on the faster member paths to match the slowest reported path. The implementation reads each stream's current delay, finds the largest, and computes each compensation as the difference from that maximum. It also updates the virtual sink's exposed latency. [PipeWire Combine Stream docs](https://pipewire.pages.freedesktop.org/pipewire/page_module_combine_stream.html), [PipeWire `module-combine-stream.c` source](https://github.com/PipeWire/pipewire/blob/master/src/modules/module-combine-stream.c#L2955-L3166)

That is the least complex automatic alignment. It does not expose a documented per-member manual offset. For measured calibration beyond what the endpoints report, use a monitorable virtual sink and separate PipeWire `module-loopback` paths to each physical sink, with a distinct `target.delay.sec` for each. The loopback module can create a virtual sink, capture a sink's monitor ports, and send the captured signal to a chosen sink. Its delay setting is a target total path latency: the implementation adds enough buffering to reach the requested target after accounting for capture and playback stream delay; it cannot subtract latency from an already slower path. [PipeWire loopback docs](https://pipewire.pages.freedesktop.org/pipewire/page_module_loopback.html), [PipeWire `module-loopback.c` source](https://github.com/PipeWire/pipewire/blob/master/src/modules/module-loopback.c#L2725-L2754)

The two physical devices do not share a clock merely because they receive the same samples. PipeWire's adapters use adaptive resampling when a device hardware clock differs from the graph clock; nodes with the same `clock.name` are treated as sharing a clock and do not get that resampler. Leave the independent local and Bluetooth clock identities alone. This manages clock-rate drift, while the combine or loopback delay buffers handle reported latency. [PipeWire audio properties](https://pipewire.pages.freedesktop.org/pipewire/page_man_pipewire-props_7.html)

Latency figures depend on device reporting. PipeWire's interface defines physical playback latency to include internal hardware rendering delay, but the Q900T's speaker/DSP delay may not be reported accurately or may vary with its Bluetooth profile. That makes empirical acoustic calibration the final check if close synchronization matters; this is an inference from the reported-latency model, not a Q900T-specific measurement. Any delay added to align the local sink with Bluetooth also delays the local output. PipeWire updates the combined sink latency, but application A/V synchronization depends on clients honoring that latency. [PipeWire latency parameter docs](https://pipewire.pages.freedesktop.org/pipewire/group__spa__param.html), [PipeWire time/latency docs](https://pipewire.pages.freedesktop.org/pipewire/structpw__time.html), [Combine Stream source](https://github.com/PipeWire/pipewire/blob/master/src/modules/module-combine-stream.c#L2970-L3029)

## Rust interfaces and responsibility split

The maintained `pipewire` Rust crate wraps `libpipewire`. Its documented client setup uses a main loop, context, core, and optionally a registry; its `Stream` API connects input or output streams and provides process callbacks and buffers. PipeWire directions distinguish a capture stream consuming a source from a playback stream producing to a sink. [PipeWire Rust crate docs](https://pipewire.pages.freedesktop.org/pipewire-rs/pipewire/), [Rust Stream API](https://pipewire.pages.freedesktop.org/pipewire-rs/pipewire/stream/struct.Stream.html), [PipeWire stream docs](https://pipewire.pages.freedesktop.org/pipewire/page_streams.html)

A Rust implementation can capture a selected sink monitor and feed one or more playback streams, or create a custom PipeWire node. That transfers fan-out, reconnection, buffer handling, and calibration policy to the process. If the requirement is only routing every ordinary host stream to two sinks, native graph configuration is smaller and lets PipeWire manage its own stream clock conversion and latency reporting. Keep Rust for a future control/status surface or for audio processing that the graph modules cannot express. [PipeWire stream docs](https://pipewire.pages.freedesktop.org/pipewire/page_streams.html), [Rust Stream API](https://pipewire.pages.freedesktop.org/pipewire-rs/pipewire/stream/struct.Stream.html)

## Constraints and risks

- The virtual sink only covers streams routed through it. Set it as the WirePlumber default and account for apps that pin another target. Use runtime sink properties for match rules rather than transient numeric node IDs. [WirePlumber default-node selection](https://pipewire.pages.freedesktop.org/wireplumber/policies/linking.html), [wpctl docs](https://pipewire.pages.freedesktop.org/wireplumber/man/wpctl.html)
- Bluetooth output needs the device's A2DP sink role for normal speaker playback. WirePlumber also supports headset profiles; its documentation notes that HSP/HFP mode has considerably lower audio quality and can be activated when capture streams trigger headset mode. Confirm the Q900T remains on its playback profile while the combined sink is active. [WirePlumber Bluetooth configuration](https://pipewire.pages.freedesktop.org/wireplumber/daemon/configuration/bluetooth.html), [WirePlumber Bluetooth settings](https://pipewire.pages.freedesktop.org/wireplumber/daemon/configuration/settings.html)
- Bluetooth availability and profile changes alter which output stream exists. The matching rules and reconnect policy must tolerate the sink disappearing and returning. WirePlumber normally reconnects a stream if its target node disappears unless configured otherwise. [WirePlumber linking policy](https://pipewire.pages.freedesktop.org/wireplumber/policies/linking.html)
- The exact module and configuration behavior depends on installed PipeWire/WirePlumber versions. The Rust binding version and system `libpipewire` ABI also need to match the supported host package. [PipeWire Combine Stream docs](https://pipewire.pages.freedesktop.org/pipewire/page_module_combine_stream.html), [PipeWire Rust crate docs](https://pipewire.pages.freedesktop.org/pipewire-rs/pipewire/)

## Recommendation

Begin with one PipeWire combined virtual sink, matched to the local sink and the Q900T Bluetooth sink, with latency compensation enabled and the virtual sink selected as WirePlumber's default. Use it for all normal host playback. If acoustic measurements show a residual offset from unreported speaker latency, switch the fan-out to separate monitor-loopback paths and calibrate their `target.delay.sec` values; retain a PipeWire-managed graph and do not put the audio relay in Rust.

No implementation or host-specific timing measurement was performed for this research task.
