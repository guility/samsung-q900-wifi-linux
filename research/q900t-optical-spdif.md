# Q900T optical/S/PDIF multichannel path

**Checked:** 2026-11-19
**Scope:** Samsung HW-Q900T optical formats, S/PDIF compressed-surround transport, and Linux passthrough support. This is a research note; no device profile or application code was changed.

## Findings

- The Q900T manual describes connecting an optical source to `DIGITAL AUDIO IN (OPTICAL)`, selecting `D.IN`, and playing its audio. The same manual explicitly says **Dolby Atmos and DTS:X are supported in HDMI mode only** (manual pp. 22–23, 27–28). That is the clearest Q900T-specific limit: optical does not provide its Atmos/DTS:X playback path. [Samsung HW-Q900T manual (PDF)](https://org.downloadcenter.samsung.com/downloadfile/ContentsFile.aspx?CDSite=UNI_UK&OriginYN=N&ModelType=N&ModelName=HW-Q900T&CttFileID=9492842&CDCttType=UM&VPath=UM%2F202402%2F20240215110810001%2FAH81-13331K-02_FM_HW-Q900T_XU_ENG_240213.0.pdf)
- Samsung's manual does not give an optical-specific PCM rate, sample-depth, or channel table. The interface standard's baseline PCM use is mono/stereo, so ordinary S/PDIF optical PCM should be treated as stereo unless a device documents a non-standard extension. [IEC 60958-1](https://webstore.iec.ch/en/publication/62829)
- Samsung's overall format list includes Dolby Digital and DTS, and the Q900T spec sheet lists DTS 5.1ch and a digital optical input. Neither Samsung document says that those formats are accepted specifically on that optical input. Therefore **optical Dolby Digital 5.1 or DTS-core 5.1 is plausible, but not confirmed for this model by the available Samsung documentation**. [Samsung spec sheet](https://image-us.samsung.com/SamsungUS/samsung/us/tvs/HW-Q900T_Soundbar_Spec_Sheet_Final_Files.pdf)
- Consumer IEC 60958 is primarily a mono/stereo linear-PCM interface; IEC 61937 defines a different, non-PCM bitstream transport over that interface. The IEC standards cover AC-3 and DTS bitstreams, so ordinary optical S/PDIF can carry compressed 5.1 when both endpoints support that codec. It does **not** carry six discrete channels of LPCM over one standard link. [IEC 60958-1](https://webstore.iec.ch/en/publication/62829), [IEC 61937-1](https://webstore.iec.ch/en/publication/62828), [IEC 61937-3 (AC-3/E-AC-3)](https://webstore.iec.ch/en/publication/67665), [IEC 61937-5 (DTS)](https://webstore.iec.ch/en/publication/64573)

The IEC capability is not a promise that every optical output or decoder accepts every codec. For the Q900T, AC-3/DTS-core support over optical still needs a physical playback check. Dolby Atmos/DTS:X require the manual's HDMI-only path; a legacy AC-3 or DTS 5.1 bitstream is not an Atmos/DTS:X stream.

## Linux support and current host

- **ALSA:** alsa-lib includes an IEC958 PCM plugin for conversion to/from 32-bit IEC958 subframes. This is interface plumbing, not an AC-3 encoder or a guarantee that a given ALSA driver exposes encoded output. [ALSA PCM plugin documentation](https://www.alsa-project.org/alsa-doc/alsa-lib/pcm_plugins.html)
- **FFmpeg:** the installed FFmpeg is 9.0.1. Its `spdif` muxer is documented as IEC 61937 for S/PDIF, and local capability inspection shows AC-3 and E-AC-3 encoders and a DTS decoder, but no DTS encoder. The supplied host check successfully generated a one-second 6-channel/48-kHz AC-3 stream at 640 kbit/s in IEC 61937 form. That proves encoding/muxing in software, not sound from the physical output. [FFmpeg 9.0 IEC 61937 muxer source](https://ffmpeg.org/doxygen/9.0/spdifenc_8c.html)
- **PipeWire/WirePlumber:** the installed versions are PipeWire 1.6.11 and WirePlumber 0.5.17. PipeWire's SPA format API models IEC958 as `mediaType=audio`, `mediaSubtype=iec958`, and a codec such as `AC3` or `DTS`; `pw_stream_connect()` accepts negotiated format parameters. WirePlumber only enables passthrough codecs configured as supported by the ALSA device. This gives a native PipeWire/Rust client a documented low-level route to request an encoded IEC958 stream, subject to device advertisement and exclusive passthrough negotiation. [PipeWire IEC958 format API](https://docs.pipewire.org/iec958-utils_8h_source.html), [PipeWire stream API](https://docs.pipewire.org/group__pw__stream.html), [WirePlumber ALSA IEC958 settings](https://pipewire.pages.freedesktop.org/wireplumber/daemon/configuration/alsa.html)
- **`pw-cat` and PulseAudio compatibility:** `pw-cat`'s normal playback options describe sample formats for PCM; the CLI exposes no IEC958 codec/passthrough option. PipeWire's PulseAudio emulation documents `ac3-iec61937` and `dts-iec61937`; this means a Pulse-compatible client can request AC-3 passthrough when the sink advertises it, using the extended stream API and `pa_format_info`. Ordinary PCM playback does not passthrough compressed audio. **This host's Pulse-compatible sink cannot accept AC-3 now because it advertises only `pcm`.** [pw-cat manual](https://docs.pipewire.org/page_man_pw-cat_1.html), [PipeWire PulseAudio modules](https://docs.pipewire.org/page_pulse_modules.html), [PulseAudio passthrough API](https://wiki.freedesktop.org/www/Software/PulseAudio/Documentation/User/Passthrough/)

**Current host evidence:** the DMI board is `MAG Z690 TOMAHAWK WIFI DDR4 (MS-7D32)`. MSI's official specification identifies a Realtek ALC4080 audio codec with optical S/PDIF output, and the datasheet labels rear I/O port 12 `Optical S/PDIF OUT`. The host's PipeWire card appears as `alsa_card.usb-Generic_USB_Audio-00` and exposes an S/PDIF sink at `s16le`, 2 channels, 48 kHz with `Formats: pcm`; the Q900T is also visible as a 2-channel Bluetooth sink. The user reports that no TOSLINK cable connects the host to the Q900T, so optical playback on the soundbar is untested. The current host exposes no AC-3/DTS optical passthrough endpoint, even though FFmpeg can create an AC-3 IEC 61937 stream and PipeWire has APIs for encoded streams. [MSI MAG Z690 TOMAHAWK WIFI DDR4 specifications](https://www.msi.com/Motherboard/MAG-Z690-TOMAHAWK-WIFI-DDR4/Specification), [official MSI datasheet](https://storage-asset.msi.com/datasheet/mb/id/MAG-Z690-TOMAHAWK-WIFI-DDR4.pdf). (The host observations are from DMI, `pactl list cards`, and `pactl list sinks`; PipeWire reports S/PDIF port availability as unknown.)

## Implications and current decision

An optical route can satisfy “compressed 5.1” with AC-3/DTS only if the chosen transmitter, driver/profile, cable, and Q900T optical decoder all cooperate. It cannot satisfy the current bridge's discrete 5.1-LPCM semantics. For arbitrary desktop PCM, a viable design would need an AC-3 encode step plus IEC 61937 output, likely as a separate exclusive stream; current PCM mixing, volume, mirroring, and channel-remap logic cannot be reused unchanged for a passthrough stream. This is an implementation inference from the codec and PipeWire negotiation models above. AC-3 is the practical software encode candidate on this host; DTS encoding is not available in its FFmpeg build.

The user confirmed that host-to-Q900T HDMI is not available and chose stereo as the immediate hardware milestone. The user then broadened the product direction to simultaneous playback on any selected connected outputs, with per-output delay compensation; Q900T is one endpoint, not the product boundary. The above-SBC quality constraint remains for the Q900T. Its current Bluetooth path is SBC, so it does not meet that constraint. Raw stereo PCM over RTP to a Linux receiver followed by stereo PCM over optical S/PDIF remains a candidate wireless route, while direct optical output from the host is a wired option if a TOSLINK cable is connected.

The host has a model-verified physical optical output, but its TOSLINK cable is not connected to the Q900T. A host `lpcm-check` sent FL/FR through PipeWire's S/PDIF sink; because the cable is disconnected, this only verifies software routing and is not an audible Q900T test. A separate Linux receiver with optical output and a TOSLINK cable would be needed to validate the wireless RTP leg through the soundbar.

For the generic synchronization goal, the user reports that a microphone is mounted approximately one metre above the soundbar and wants microphones used for automatic delay detection. PipeWire currently exposes USB Audio Mic/Line and Logitech BRIO capture sources; the exact source used by the mounted microphone has not been identified, and no acoustic calibration recording has been made. A first practical design is to emit known probes through selected outputs, capture them on one microphone clock, estimate relative arrival times at this fixed point, and delay earlier outputs. This is a design direction, not implemented behavior; it measures one acoustic location and does not by itself compensate clock drift.
